# Graduate Email Code Sign-in Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let FGS-approved graduates verify one approved mailbox and access their existing student record without Passport York, with Google remaining an independent alternative.

**Architecture:** Add separate email approvals, historical connections, active-address mappings, browser-bound challenges, and a database enable/generation control. Use Delayed Job's Active Record backend for identifier-only jobs and primary-database transactions for shared throttles and authentication issuance. Generalize graduate sessions with an explicit email connection foreign key while preserving Google's provider/UID identity model.

**Tech Stack:** Existing Ruby 3.1.4, Rails 7.0.8.1, MySQL/InnoDB, SQLite tests, Minitest/Capybara/Selenium; add pinned `delayed_job` 4.1.13 and `delayed_job_active_record` 4.1.11. No Redis, PostgreSQL, Rails, Ruby, or database upgrade.

## Global Constraints

- FGS verifies an existing graduate using its actual approved procedure and explicitly confirms one individual address. No account creation, contact matching, contact-field enrollment, Google email matching, or automatic aliases.
- Staff retain Passport York. Only active administrators/managers outside impersonation can issue, cancel, recover, or revoke email access. Student email sessions never gain staff privileges or Passport York linking authority.
- Invitations expire after **48 hours**. Generate **six digits**, retaining leading zeroes; challenge expiration is **five minutes from creation**, including queue/delivery time; maximum **five failed attempts per challenge**.
- Send limits: **one per address per 60 seconds**, **five per rolling hour per address**, **20 per rolling hour per IP**. Limits are shared and atomic. Accepted resends replace only the same browser transaction and purpose; throttled requests change no previous challenge. Send throttles do not block verification.
- Aggregate verification rules below apply across enrollment, login, browsers, resends and replacements. Never permanently block a student because of OTP requests or guesses.
- Store only a context-bound keyed code digest with a dedicated secret. Jobs contain one opaque identifier, never code, recipient, invitation token, mail body, or serialized model. Code exists only in worker memory and recipient mail.
- CSRF-protected POST send/verify/revoke actions, HTTPS, no-store pages, clean URLs after invitation entry, no analytics or secret-bearing logs/artifacts. Codes never appear in URLs.
- Database-authoritative default-off email enable state and monotonically increasing generation. Missing/unreadable control, secrets, locks or dependencies fail closed for email. Disable advances generation; old approvals/challenges/jobs/sessions never revive. Google and Passport York stay independent.
- One active connection per student and one student per normalized address, with two non-null independent database unique indexes on a separate active mapping. Preserve historical connections.
- Write failure scenarios first. Prefer browser E2E. Necessary database/worker isolation checks are specified and written before their implementation; never add unit tests after code. No new unit-test suite is planned.
- Preserve existing auth harness setup, CSRF settings, trusted PPY test boundary, browser waits and cleanup conventions. Fix only waits required by this feature using destination/content assertions, never sleeps or blanket retries.
- Plain commit subjects without Conventional Commit prefixes. No push without explicit current-context user approval. This planning round changes only this file, does not commit, delegate, install, migrate, send mail, or implement code.
- Local verification, QA real-mail/FGS readiness, and production activation are separate gates. Neither a green suite nor plan approval authorizes deployment/activation.
- Initializers must boot safely before email tables exist and after migration rollback; email remains unavailable, while existing application behavior remains usable. Queue admission, cleanup and worker configuration apply only to graduate-email jobs, preserving unrelated queued rows and the existing Active Job adapter.

## Review Focus

1. An expired or disabled transaction resumes in a dormant browser after re-enable: reject its approval, challenge and session; a verified connection may request a new challenge (Tasks 2, 5, 7).
2. A worker dies around SMTP acceptance or runs twice: never regenerate/retry a claimed code, distinguish reported failure from unknown acceptance, and allow only precisely permitted states to verify (Task 4).
3. Different browsers, enrollment/login, or a replacement address evade limits: shared address, student and IP verification budgets survive each transition; another browser's resend leaves a valid code intact (Tasks 3, 6, 7).
4. Case, whitespace, plus/dot variations, header injection and database collation disagree: one canonical parser/key drives indexes, lookups, mail recipients and throttles on both databases (Tasks 1, 3, 6).
5. Failure screenshots, exception notifications or debug mail instrumentation disclose secrets: capture only clean screens, suppress automatic secret-screen artifacts and raw mail/error payloads, and scan reports without printing matches (Tasks 1, 4, 7, 8).

## Shared contracts to implement

### Persistence and normalized equality

Use integer FKs to `users` for student/staff, matching existing tables, bigint FKs for new tables. Authorized existing student destruction cascades student-owned approvals/connections/mappings/challenges/sessions/notices; history remains on ordinary revocation/replacement. EVERY audit FK is nullable with explicit database `on_delete: :nullify` (SQL `ON DELETE SET NULL`): `actor_id -> users`, `student_id -> users`, `approval_id -> graduate_email_approvals`, `connection_id -> graduate_email_connections`, and `challenge_id -> graduate_email_challenges`. Audit associations are optional and never use dependent destroy/delete cascades from any referenced model. Audit event/outcome/generation remain intact when any reference disappears, including ordinary challenge cleanup and authorized student destruction. Separately, the approving-staff FKs on approvals/connections remain restrictive while those records are retained for verification; they are not audit FKs. Explicit cascade edges on approval/connection challenges and old/new notice connections prevent deletion-order errors. Test the existing manager student-delete route, not just individual model deletion. All times use UTC database instants; windows use one `Time.current` per transaction, never browser time. Require NOT NULL/check constraints for essential state, plus application validation. Primary database only, no replicas/cached `AppSettings` for auth state.

`GraduateEmail::Address.normalize(input:) -> String | nil`: trim surrounding ASCII whitespace, lowercase ASCII local/domain, preserve plus tags and dots; accept exactly one unquoted ASCII addr-spec, max 254 bytes/local 64 bytes with a valid domain. Reject display names, lists, separators, embedded whitespace/control/CRLF, Unicode/IDN input and malformed domains with a clear staff validation error. This deliberately conservative first version requires FGS to use a supported individual mailbox; no implicit punycode or alias conversion. Use existing `mail` parsing plus exact round-trip/grammar checks, not contact recipient helpers. Canonical value is the delivery recipient and lookup value. Store normalized-address strings with explicit `utf8mb4_bin` on MySQL and default `BINARY` on SQLite; accepted strings have no spaces/non-ASCII, so trailing-space/accent rules cannot introduce a second equality. Use the same parser everywhere. HMAC-SHA256 canonical address/IP keys with domain-separated `GRADUATE_EMAIL_LIMIT_KEY`, never raw addresses in throttle keys.

### Atomicity, limits and resource bounds

`GraduateEmail::Control.synchronize { |control| ... }` opens a fresh primary transaction whose **first SQL operation is a write** `UPDATE graduate_email_controls SET lock_version = lock_version + 1 WHERE id=1`. Require exactly one affected row, then read state. This serializes short OTP database mutations on MySQL and acquires SQLite's database write lock before reads. No SMTP, network call, mail rendering, process wait or other external I/O runs inside this or any student/challenge transaction. Fail closed on missing row/timeout. Deterministic order for email operations: control, student IDs ascending, approvals, connections, active mappings, challenges, graduate sessions, limit records, notices (each table by ascending ID). Lock student before evaluating active state or touching subordinate records; any unlocked lookup is only a hint and must be revalidated under locks. Control transitions change only control/audit state, not student records en masse.

Preserve `Student`'s existing `after_update :revoke_graduate_sessions_on_block` and ordinary `save`, `update`, `update_attribute` and inherited `User#block` paths. Extend that callback inside the existing student update transaction: when blocked changes to true, revoke both session methods, pending email approvals and challenges, and active email connection/mapping through `Revocation.for_student_locked!(student_id:)`, taking only the subordinate locks in the order above. It never reads or acquires email control, never checks feature enablement, and never depends on SMTP/queue availability. Move existing session revocation into this ordered primitive rather than locking sessions ahead of email artifacts. Do not override `Student#block`, reject legacy saves, or change UsersController. Missing/disabled control cannot prevent staff blocking; schema/database failures still roll back the transaction normally. Raw SQL/`update_columns` bypass callbacks and are not claimed to revoke artifacts. Unblock restores no approvals, connections, challenges or sessions; fresh FGS enrollment is required for revoked email access.

Deadlock argument: email issuance/redemption locks control then student before subordinates; a block already holding student never waits for control, so it can finish while an email transaction waits for student. No subordinate-lock holder may later acquire student/control. Google issuance retains its student-first transaction and must check blocked state under that lock; it never acquires email control. SQLite serializes writes at the database level, with no network wait inside its write transaction. Validate these orders with independent DB sessions, including Google issuance and direct model/controller block paths.

`Control.enabled? -> Boolean` always does an uncached primary read and returns false on failure; email mutation callers additionally require locked enabled state/current generation. `Control.set_enabled!(enabled:, actor_id:) -> Integer` serializes under control: disabling advances generation even if already disabled; enabling retains the latest generation and records a safe audit. No cache/session/environment toggle overrides this row. Enrollment issuance, delivery claim/final eligibility, verification and session issuance recheck generation under control. Each email-authenticated request validates state/generation on primary under the wrapper. An already-authorized HTTP response can finish; no verification/session issuance may linearize after disable. An already-authorized/in-flight SMTP call may deliver stale mail after disable, revoke, block or resend, but invalidated code cannot authenticate. No retraction or exactly-once SMTP promise; re-enable never restores old generations.

Atomic sliding windows, shared across workers and purposes:

- Address sends: prior accepted sends >=5 in `(now-1h, now]` or most recent send less than 60 seconds ago denies. Reserve only an eligible real send; do not reset on resend or failure.
- IP requests: allow first 20 send requests in a rolling hour, count admitted request attempts including unknown/unenrolled/throttled addresses, so address state does not determine the IP counter. Refuse the 21st. After global admission, check IP admission before address lookup/key creation. IP rejection writes no new IP event/cooldown, address/student key, real challenge or per-target audit.
- Verification failures: address **10/15 minutes**, student **10/15 minutes** across old/new addresses and enrollment/login, IP **50/15 minutes**. The threshold failure is recorded then begins **15-minute cooldown** on that key. While cooling down, reject all verification for that key, do not extend cooldown on rejected requests. At cooldown expiry clear that key's failure-window events atomically to allow fresh attempts. Never clear budgets on success/resend/replacement/disable/re-enable. Existing challenge still has its own five-failure ceiling.
- A malformed/wrong/reused/cross-browser attempt counts toward IP; if it identifies a server-bound real transaction, also address/student. Never trust posted address/student IDs for selection or for resetting a budget. Correct code after cooldown still needs unexpired challenge/current state. Requests blocked by send limits may still verify unless verification limits apply.
- Global capacity independent of existence: at most **120 admitted send operations/minute**, **300 verify operations/minute**, and **500 retained OTP/noop queue rows**, counting queued, locked, failed and terminal rows, not only runnable jobs; notices have a separate 50-row reserve. Evaluate global admission before target lookup or IP/address/student record creation. Saturation returns the identical generic page/status, writes no per-request record, and leaves existing challenges unchanged. Within admitted global/queue capacity, every send request enqueues exactly one real or noop challenge/job atomically. IP/address-throttled requests use noop only within that capacity. Unknown/disabled/blocked/unenrolled noop rows have null address/student/approval/connection references; no per-address cooldown or audit is created. Retain only an opaque browser digest/public ID and generation/expiry for the equivalent asynchronous path. Compute address keys only after global and IP admission; unknown targets need no persisted address key. If database/control is unavailable, skip queue work uniformly and show the same generic send response.
- Resource retention is part of the bound: no request-level audit for unknown, global/IP-rejected or noop traffic; operational failure metrics have fixed enum keys, with no address/IP labels or per-request database rows. These metrics are diagnostic only and never enforce security limits. Admission/limit events expire after two hours; noop/real challenges after 24 hours past expiry. Successful jobs delete immediately, failed jobs use `destroy_failed_jobs?=true`; cleanup removes expired unclaimed jobs and expired abandoned claims without reexecution, plus remaining terminal rows after at most 24 hours. Capacity counts all retained rows, so cleanup failure reduces admission instead of growing the queue. Hourly cleanup (Task 8), indexed expiry and batches <=500 bound event/challenge accumulation by global admission rate times retention plus one cleanup interval; unique-IP events/cooldowns also have that bound. Only successful authentication and authorized staff/control changes create retained policy audits. Send/verification failure categories use fixed aggregate counters, not per-request permanent audits, including failures against real connections; attacker-only requests cannot grow policy history indefinitely. Do not enable before the scheduled cleanup and sustained-unknown-request gate pass.
- Maximum body 2 KiB, address 254 bytes, code exactly six ASCII digits, reject oversized requests at proxy and Rails boundary. Bound lock acquisition to two seconds for HTTP paths, one retry at most only for pre-external-effect deadlock/busy failures, total HTTP budget five seconds. Global bounds apply to verification failures too. Edge global/IP request caps are required for pre-DB traffic; do not expose an endpoint for inspecting queue/delivery/account state.

The shared lock covers short database work only. SMTP stalls occupy dedicated worker capacity without holding database locks; ordinary Google/PPY requests and staff blocking do not depend on email control. QA measures lock waits and responsiveness under a stalled relay before enablement.

### Delivery state machine and linearization

| Persisted state | Verify allowed? | Worker action and transition |
| --- | --- | --- |
| queued | No | Single claimant checks feature generation, target/student/approver/expiry/browser validity; creates six digits with `SecureRandom.random_number(1_000_000)` formatted `%06d`, stores contextual HMAC and `claimed_at`, commits state `claimed`. Plaintext stays in that worker only. |
| noop | No | Consume job without generating code, loading mailer or sending. |
| claimed | No | Original worker alone performs final eligibility transaction; valid claim becomes `sending` with `send_authorized_at`, otherwise invalidates it. Duplicate invocation does nothing. |
| sending | Yes, subject to every other check | Final eligibility committed before SMTP. Code may have escaped even if final update is lost. Never regenerate/retry; duplicate invocation does nothing. |
| sent | Yes, subject to every other check | SMTP acceptance recorded, not proof of mailbox delivery. Duplicate invocation does nothing. |
| failed | No | Reported delivery error conditionally marks failed and clears digest; no retry, approval remains pending. |
| superseded / revoked / consumed | No | Terminal. Queued/duplicate worker and finalizer cannot overwrite. |
| expired | No | Expiration predicate applies to every state, even before cleanup. Final eligibility rejects expiry; an authorized in-flight email may arrive after expiry and remains unusable. |

Delivery has three short database transactions: claim, final eligibility immediately before network I/O, and conditional finalization. Claim and final eligibility use control/student/subordinate order, rechecking enabled generation, target/approver/student/browser replacement and expiry. Commit final eligibility, release **all** DB locks/transactions, render/build mail in memory and perform bounded SMTP. Retain the committed claim identity (public ID, generation, claimed_at and digest) in memory. Finalization reacquires the normal order and updates only a matching `sending` claim with unchanged generation, unexpired/current eligible target and no consumption/invalidation. Missing control or any stale condition makes finalization a no-op; it never overwrites consumed/revoked/superseded/failed state or advances a stale-generation row to sent. An explicit reported error clears the digest only if that conditional claim still matches. No finalizer creates a session or consumes approval.

Disable/revoke/block/resend can commit while SMTP stalls. If they precede final eligibility, no send occurs. If they follow that commit, SMTP may deliver stale mail, including after they return; subsequent verification still checks authoritative generation, student and target state under locks and rejects it. There is an unavoidable interval between authorization and network send; do not claim withdrawal, exactly-once SMTP, or lock-free atomicity across database and relay.

Crash before claim commit leaves queued and may be claimed once later. Crash after claim commit but before final eligibility leaves claimed, unverifiable and never retried; graduate explicitly resends. Crash after authorization but before SMTP leaves sending with an unrecoverable in-memory code; never retry. Crash after SMTP acceptance before finalization leaves sending, verifiable until expiry only if all current checks permit it. Crash after sent commit before queue acknowledgement yields duplicate no-op. DB failure after reported SMTP error leaves ambiguous sending; a fresh conditional failure update is attempted when possible, with no mail retry. A code actually delivered in an ambiguous outcome can work only while stored state/current eligibility allows it, as the spec permits. Cleanup never reclaims claimed/sending work for delivery.

Use `GRADUATE_EMAIL_CODE_KEY` >=32 random bytes from secret store; HMAC-SHA256 over version/purpose/public_id/browser_digest/target ID/generation/code with unambiguous length-delimited encoding. Use constant-time comparison for equal-length digests and input guards. Separate code key from limits key and Rails session secret. Key rotation requires disable first, discard outstanding challenges and reissue approvals in the new generation; verified connections remain.

SMTP open/read timeouts <=3 seconds each plus total delivery deadline **10 seconds**, below worker 30 seconds. Any timeout is conservatively failed if recorded; no retry. Verify expiry in the final eligibility transaction; SMTP deadlines hold no database lock. Use mailer's own logger disabled, no SMTP protocol debug, no raw exception notifier, no globally muting logger for other threads. Safe worker errors emit enum plus record ID only; strip original exception context before anything reaches Delayed Job `last_error` or notifier. Do not allow Action Mailer process/deliver instrumentation to publish args/body for this mailer: define these as explicit class builder methods on the dedicated mailer rather than Action Mailer action dispatch: set private instance variables, render the dedicated text template with `render_to_string` and no secret-bearing locals, construct a `Mail::Message`, set the approved SMTP/test delivery method, and call that message's `deliver!` directly. Do not invoke ActionMailer `process`, `deliver_now` or `deliver_mail`, whose event payloads include arguments/body; test actual Rails subscribers at DEBUG. Other mailers retain behavior. No external subscriber/APM may capture OTP render args, body, SMTP exception or request fields.

Recovery notice: enrollment replacement transaction revokes old connection/challenges/sessions, switches mapping, creates new connection and notice/outbox job atomically. `GraduateEmailNoticeJob.new(notice_id)` claims once in a short notice-row transaction, releases every lock, then delivers `GraduateAuthenticationMailer.access_changed(old_connection:)` directly and conditionally finalizes that claim in a separate short transaction; no invitation, new address, code or session link. Duplicates/crashes never retry claimed notices; FGS sees safe notice outcome and may follow up through its procedure. Failed notice never rolls back secure replacement or restores old access. Initial enrollment is not replacement. Feature disable does not suppress a previously required security notice, but recipient is always the immutable old connection.
